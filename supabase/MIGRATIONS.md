# Applying migrations

**One baseline (plan 2 item A6, N1075, N786).** Since 11 November 2026 the
migration history is one file, `supabase/migrations/20261111130000_baseline.sql`,
generated by `scripts/baseline/build-baseline.mjs` from a database built from
the 298 files it replaces and proven to build the same database
(`docs/plans/2026-11-a6-baseline-proof.md`). Those 298 files, unchanged, and
this record as it stood (2,239 lines, one section per file) are kept in
`supabase/migrations-archive/`, out of the runner's and the CLI's path.
Nothing in the archive is ever edited (`tests/ci/migration-order.test.ts`).
A new migration is dated after the baseline and gets its own section and row
below, newest first, as before.

**The runner** (OS-W10): `scripts/apply-migration.mjs`. A run is a dry run
unless it says `--apply` with the code that dry run printed:

```bash
node scripts/apply-migration.mjs --target shared-dev supabase/migrations/<file>.sql
node scripts/apply-migration.mjs --target shared-dev --apply --confirm <code> supabase/migrations/<file>.sql
node scripts/apply-migration.mjs --target shared-dev --status   # read-only: applied vs on disk, as JSON
```

Every file in `supabase/migrations/` gets a row below, and its "Applied to"
cell is `not applied`, `shared-dev YYYY-MM-DD`, `staging YYYY-MM-DD` or
`production YYYY-MM-DD` (several joined with `; `). `tests/ci/migrations-md.test.ts`
enforces it. For the baseline the cell says where it is *recorded*: on shared
dev and staging it is never run (step 5 below), and on a new database it is
the one file applied.

`--target` names a project in `supabase/migration-targets.json` and must be
the project `.env.local` (or `--env-file`) points at. The connection verifies
the server's certificate against Supabase's root CA
(`supabase/certs/supabase-root-2021-ca.crt`) and its hostname. Each file runs
in one transaction with its row in `supabase_migrations.schema_migrations`; a
recorded file is skipped, and a destructive baseline is refused on a database
with any table in `public`. Details: "Applying without Docker or psql" below.

**Working rules for a migration pull request** (in force from 10 November 2026; `docs/plans/2026-11-work-review-remediation-plan.md`, workstream 1, from the work review's findings #125, #126 and #128):

- **Approved, then applied (R2).** A migration is applied to shared dev or staging only after the reviewing session has approved its pull request. The order is: review approves, apply with the runner to shared dev, then staging, fill both cells, then merge.
- **Dated when next to merge (R3).** Give a migration file its timestamp when its pull request is next to merge, not when it is written.
- **An applied file is never edited.** Once a file has been applied to any database, its bytes are final, merged or not. A further change is a new migration.
- **At most three in review (R1).** No more than three pull requests that carry a migration are in review at once, across every session.
- **Functions are closed by default (A3).** A new function is not executable by `PUBLIC`, `anon` or `authenticated` until a migration grants it, and pins its `search_path`. A helper function that is called on a member's behalf (from a trigger function, a policy or a default that is not `SECURITY DEFINER`) needs its own grants, because new functions are closed by default. Functions made by `create extension` are closed to `PUBLIC` too: grant what queries use, and check the snapshot.

**Staging stays level with shared dev** (R-staging-behind). A migration PR is applied to shared dev *and* staging after its review is approved and before it merges, by the same session, with both cells filled. `tests/ci/migrations-md.test.ts` lets a row name `shared-dev` without `staging` (or say `not applied`) only while the file is less than two days old by its timestamp. A session that cannot reach staging lists the file in `supabase/migrations-staging-pending.json` with the reason, and the next session with the credential applies it and removes the entry.

**A merged migration is never renamed** (#97). Apply order on every target is merge order, so filename order must stay the same as merge order. A pull request may only add migration files, each with a timestamp later than every file already on `main`, and may never rename or remove a file `main` has. The one exception was A6's: the history moved, byte for byte, to `supabase/migrations-archive/`. `tests/ci/migration-order.test.ts` fails a PR that breaks either rule, naming the file.

**After pulling A6, on a local stack:** an existing local volume recorded the old file names, so `supabase start` would try to run the baseline over a full schema. Run `npx supabase db reset` once (it rebuilds the local database from the baseline; local data is lost). A new stack needs nothing.

## How the runner works

### Applying without Docker or psql

`supabase db dump` and `supabase db start` need Docker; `supabase db query`
can't take a multi-statement file (it uses a prepared statement, which Postgres
refuses for multiple commands). So files are applied over the direct IPv6
connection with `node-postgres`, which uses the simple query protocol and
accepts whole scripts including `DO` blocks. `scripts/apply-migration.mjs` is
that runner (OS-W10, readiness N131 and N246):

- **Target.** `--target <name>` is required, must be in
  `supabase/migration-targets.json` (shared dev and staging today; production
  is added by a reviewed PR), and must be the project the env file points at.
  `.env.local` alone never decides where a migration goes.
- **TLS.** The connection trusts only Supabase Root 2021 CA (shipped in
  `supabase/certs/`, pinned by SHA-256 in `scripts/lib/supabase-db.mjs`) and
  checks the hostname against the certificate. A certificate from anywhere
  else, one for another host, or a server that won't do TLS fails the
  connection. There is no switch to turn this off.
- **Dry run first.** Without `--apply` the runner connects, reads in a
  read-only transaction (who it is, Postgres version, TLS, how many tables
  `public` has, the recorded history) and prints each file's plan (apply,
  skip, refuse) and a confirmation code. `--apply --confirm <code>` only runs
  when the code matches the same target and the same files byte for byte.
  The dry run doesn't execute the SQL: to rehearse what a file does, run it
  against a copy.
- **History in the same transaction.** Each file runs inside one transaction
  the runner opens. Statements are found with a PostgreSQL-aware lexer
  (`scripts/lib/sql-statements.mjs`: strings, quoted identifiers, nested
  comments, dollar quotes), so a file's own outer `begin;`/`commit;` (or
  `end;`) is removed, and any other top-level `COMMIT`, `END`, `ROLLBACK`,
  `ABORT`, `BEGIN`, `START TRANSACTION`, `SAVEPOINT`, `RELEASE`,
  `PREPARE TRANSACTION` or `COMMIT/ROLLBACK PREPARED` refuses the file, as do
  `CONCURRENTLY`, `VACUUM` and `BEGIN ATOMIC`,
  under an advisory lock, and its row goes into
  `supabase_migrations.schema_migrations` (version, name, the file's text) in
  that transaction. A failing file leaves neither its changes nor a row. The
  runner creates the history table (the CLI's shape) on first apply.
- **No replay.** A version already in the history is skipped.
- **No baseline on a populated database.** A file that is marked
  `-- DESTRUCTIVE` or drops a schema (0001) is refused when `public` has any
  table, both in the dry run and again inside the apply transaction. Nothing
  overrides this.
- **Risky SQL needs an allow-list entry on a populated database.** A
  top-level `TRUNCATE` or `DROP TABLE`, the same run directly inside a `DO`
  block or a function the file creates and then calls, or dynamic SQL
  (`EXECUTE` there) that destroys data or can't be classified from its
  leading literal, is risky. Bodies are read in any quoting (dollar quotes,
  `'…'` with doubled quotes, `E'…'` escapes, nested `DO`s), and a body that
  doesn't parse counts as risky; temporary tables the body creates are
  exempt. A risky file is refused when `public` has tables unless `supabase/migration-targets.json` `dynamicSqlAllowed`
  names the file, the sha256 of its exact bytes and a reason. The list is empty
  since plan 2 item A6 (its two files are archived); a test fails if a risky
  file has no entry or an entry goes stale.

Several files can go in one run (they are sorted by name and each gets its own
transaction; the run stops at the first failure). PostgREST is told to
reload its schema after each committed file, so a later failure can't leave
an applied file unannounced, and once on an apply run that finds everything
already recorded. `scripts/import-vehiclesdb.mjs` uses
the same target check and TLS.

### Recording without running (`--record-only`)

`--record-only` writes a history row without running the file, only when
every object the file creates is verified on the target, read-only
(functions by signature and body, `scripts/lib/migration-objects.mjs`). Same
dry run, `--confirm`, allow-list and TLS. It is how the baseline is checked
against shared dev and staging before their history is replaced (step 5);
the full description of what it verifies, refuses and cannot see is in
`supabase/migrations-archive/MIGRATIONS.md`, "Recording without running".
Plan 2 item A6 step 7 removes it once nothing needs it.

**Do not use `supabase db push`** against shared dev or staging. Their CLI
history is the runner's, and the runner is the only thing that applies files there.

## Verifying on a throwaway database

Every migration, SQL guard and the generated types are proven on a disposable
Postgres before anything reaches a hosted project, never on one. The recipe is
CI's `sql-guard` job:

```bash
bash scripts/disposable-db.sh start 55440        # CI's image and shim, then every file in supabase/migrations/
PGPASSWORD=postgres PGHOST=127.0.0.1 PGPORT=55440 bash scripts/test-sql-guards.sh
DRVN_TYPES_DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:55440/postgres node scripts/generate-database-types.mjs --check
docker rm -f drvn-disposable-55440
```

The shim is for that database only: never apply `supabase/tests/ci_shim.sql`
to a hosted project.
