## Overall assessment

The report is a useful launch-risk inventory, and several of its most serious findings are supported by the code: missing buyer recourse before dispatch, unsafe media deletion, unguarded admin reads, incomplete account erasure, and unredacted AI history. However, its “Checked” confidence is sometimes too strong: dependency advisories, hosted backups, branch protection and deployed authentication settings cannot be established from this checkout. It also contains factual errors, overstates some consequences, and misses additional privacy and money-state vulnerabilities. **My judgement is no public launch or unrestricted live payments yet**, principally because of B2, B4, B5 and the additional issues below. I reviewed this read-only, traced relevant definitions through the 218 migrations, and made no network calls or test/build runs. Consequently, the report’s test results and external security-advisory claims remain independently unverified.

## Missed issues

### X1 — Blocker: media deletion can bypass references through URL encoding

**Evidence:** [reference comparisons](/Users/neilbarrow/Desktop/Cursor%20Projects/DRVN%202/src/lib/media-lifecycle.ts:31), [path decoding](/Users/neilbarrow/Desktop/Cursor%20Projects/DRVN%202/src/lib/media-url.ts:118), [privileged deletion](/Users/neilbarrow/Desktop/Cursor%20Projects/DRVN%202/src/lib/media-lifecycle.ts:127), and `m/20261017140000_rls_initplan.sql:389`.

Reference checks use the supplied URL string, while `parseStorageObject` decodes the object path before deletion. A staged URL with a percent-encoded character in a filename can therefore fail to match the canonical URL stored in galleries or order snapshots yet resolve to the same physical storage object. The staging policy does not validate URL/path ownership or canonical form.

**Impact:** B5 is broader than dispute evidence: a signed-in attacker with an object URL can potentially erase referenced public photos, including purchase evidence. This is a static code-path finding; no destructive reproduction was performed.

**Fix:** Remove arbitrary client staging writes, authorize by owner, and identify references by canonical `(bucket, object_path)` rather than URL spelling. Canonicalize before every ownership/reference comparison. Include encoded-path cases in verification.

### X2 — High: a buyer can locally close a Stripe chargeback and restore payout eligibility

**Evidence:** [closeDispute](/Users/neilbarrow/Desktop/Cursor%20Projects/DRVN%202/src/features/commerce/dispute-actions.ts:283), `m/20260905195518_provider_dispute_ordering.sql:105`, `m/0020_transfer_scheduling.sql:74`, and [transfer eligibility](/Users/neilbarrow/Desktop/Cursor%20Projects/DRVN%202/src/lib/payments/transfer-worker.ts:420).

`closeDispute` checks buyer ownership and `status === "disputed"` but does not read or reject `stripe_dispute_id`. It restores `pre_dispute_status` using the service role. A chargeback opened after delivery can consequently return locally to delivered/completed while its provider journal remains open. Payout readiness checks order status and release time, without consulting that open journal.

**Impact:** The platform can release seller funds while the bank dispute remains active, increasing unrecoverable chargeback exposure. The buyer’s action cannot actually withdraw the bank case.

**Fix:** Separate provider disputes from member disputes. Reject member close/refund-resolution commands for provider-owned cases, and independently exclude open/recovery/loss-pending provider disputes from payout eligibility.

### X3 — High: a token refund offer disables automatic refund indefinitely

**Evidence:** [positive refund amount accepted](/Users/neilbarrow/Desktop/Cursor%20Projects/DRVN%202/src/features/commerce/dispute-actions.ts:79), [buyer escalation refusal](/Users/neilbarrow/Desktop/Cursor%20Projects/DRVN%202/src/features/commerce/dispute-actions.ts:341), and [SLA exclusion](/Users/neilbarrow/Desktop/Cursor%20Projects/DRVN%202/src/lib/payments/dispute-sla.ts:76).

A seller can offer a one-cent refund. Any outstanding refund offer blocks the buyer’s escalation action; any non-null `refund_offered_at` excludes the case from the day-ten automatic refund. There is no expiry in these paths.

**Impact:** A seller can keep a legitimate dispute unresolved by making a nominal offer. The daily SQL escalation and admin intervention still exist, so this does **not** eliminate every support remedy (`m/0021_dispute_sla.sql:37`), but it defeats the advertised self-service/automatic safety net.

**Fix:** Add offer expiry and a buyer rejection action. Permit escalation despite an unacceptable offer, and retain a case-resolution deadline independent of seller offers.

### X4 — Medium: dispatch spends tracking-provider resources before seller authorization

**Evidence:** [markShipped provider call](/Users/neilbarrow/Desktop/Cursor%20Projects/DRVN%202/src/features/commerce/order-fulfillment-actions.ts:45), followed by the authorizing RPC at `:62`.

For high-value paid orders, the action reads status/total using the service role and calls `createTracker` before checking whether the signed-in caller is the seller. The database later refuses unauthorized dispatch, but the external request has already happened. No action-specific rate limit precedes it.

**Impact:** A signed-in caller with a paid order ID can cause unauthorized tracking requests and consume quota or incur provider cost without successfully changing the order.

**Fix:** Verify seller ownership before any provider interaction; rate-limit tracker creation and reuse an already registered tracker where appropriate.

### X5 — High: photos belonging to private cars are public storage objects

**Evidence:** `m/0001_v3_schema.sql:385`, [public car-photo upload](/Users/neilbarrow/Desktop/Cursor%20Projects/DRVN%202/src/app/api/media/public-photo/route.ts:68), and `m/20261017140000_rls_initplan.sql:102`.

Database policies hide private car/gallery rows. Storage’s public-read policy nevertheless permits reads for the entire `car-images` bucket, and the uploader always creates a public URL. Making a car private does not alter that storage access model.

**Impact:** Someone with a photo URL can access images from a private car. This is distinct from the report’s deleted-media issue: the car can be private from the outset.

**Fix:** Define whether “private” promises photo confidentiality. If it does, use private originals with authorization-bound signed access, and publish separate public copies only when appropriate. Address cached copies when changing visibility.
