# A6 analysis: one baseline in place of the migration history

**Draft for review, 10 November 2026.** Written by the plan 2 building session for the orchestrator, before the quiet point. It is analysis only: nothing here has touched shared dev or staging, no migration file has been moved, and no baseline exists yet. It prepares plan 2 item A6 (`docs/plans/2026-11-architecture-remediation-plan.md`).

Every number below was measured on `main` at `af047e6` (287 migration files) on throwaway databases built the way CI's `sql-guard` job builds one: the pinned image `supabase/postgres:17.6.1.165`, `supabase/tests/ci_shim.sql`, then every file in `supabase/migrations/` as `supabase_admin`. The tools used are on the branch `docs/a6-baseline-analysis`: `scripts/schema-snapshot.mjs` (plan 2 item A1), `scripts/baseline/classify-migration-statements.mjs` and `scripts/baseline/outside-catalog.sql`.

---

## 1. In plain words

A6 replaces 287 files with one file that builds the same database. The risk is that the one file builds a database that looks the same and is not. This document says where that would happen, how each case will be carried across, and the exact test that will show the two databases are identical.

Five things were found that the plan did not know. Each was measured, not reasoned.

1. **A copy made with the standard tool would open the database up.** The obvious way to make the one file is `pg_dump`, Postgres's own export tool. A trial showed that a database rebuilt from that export lets a signed-out visitor run **308 functions** they cannot run today, lets a signed-in member run **237**, and gives both roles full table privileges on **101 tables**. The export is not wrong; Supabase gives every new object extra permissions at the moment it is created, and the export does not know to take them away. Section 4 has the detail. The baseline will write every permission out in full and will not rely on the export for them.
2. **The curated list of car generations is not in a new database, and its only copy is inside one of the 287 files.** The migration that holds the 194 curated generations joins them to the vehicle catalogue. In a new database the catalogue is empty, so the migration inserts nothing. The list reaches a database only when `scripts/import-vehiclesdb.mjs` runs, and that script reads the list out of the migration file by name. Moving the file to an archive would break the import. Section 3 has the fix.
3. **The numbers in the plan are slightly off.** There are 287 files and 60,173 lines today (the plan says 286 and 59,722: PR #201 merged since). There are 8 storage buckets, not 5, and 13 storage rules, not 20. There are 21 scheduled jobs, as the plan says. 64 files hold top-level data statements, not 63, and seven more change rows through a function call or a `DO` block.
4. **The same database prints differently depending on who reads it.** Postgres shows `orders` to a reader whose search path includes `public` and `public.orders` to one whose path does not, and the two administrator roles have different paths. A comparison made carelessly would report hundreds of false differences, or hide real ones. The snapshot tool now pins this and refuses to run otherwise.
5. **There are three kinds of database to prove, not one.** CI's guard database, the local Supabase stack the browser tests use, and a hosted project are built by different roles with different storage and sign-in tables. "Identical" has to be shown in the first two and checked against the third. Section 5 says how.

Nothing found here says A6 should not be done. It says the baseline must be generated by a script that is itself reviewed, and that the proof must compare permissions line by line.

Seven more change rows another way: three call a function that writes, and four do it inside a `DO` block (two with a direct update, two by calling a function).

## 3. The curated vehicle generations

`supabase/migrations/20261020100000_vehicle_generations.sql` ends with a list of 194 curated generations (Golf Mk1 to Mk8 and so on), written as an `insert … select` that joins the list to `catalog_makes` and `catalog_models`.

- In a new database those two tables are empty, so the insert adds **no rows**. A fresh build of all 287 files has an empty `vehicle_generations` table. Measured.
- Shared dev has the rows, because its catalogue was filled before that migration ran.
- For any other database the rows arrive when `scripts/import-vehiclesdb.mjs` runs. That script calls `generationSeedSql()` in `scripts/lib/vehicle-catalog.mjs:70`, which opens `supabase/migrations/20261020100000_vehicle_generations.sql` and cuts the list out between two comment markers. The comment there says this is deliberate: one copy of the list.

So the plan's statement that the baseline must carry "the curated vehicle generations" as reference rows is not what a faithful baseline does. A baseline that is identical to the 287-file build has none. What must survive is the list, as a file the import can read.

**Proposed handling (for the orchestrator to confirm).** In the A6 pull request the list moves, byte for byte, to its own file, `supabase/reference/curated-vehicle-generations.sql`, and `GENERATIONS_MIGRATION` points there. The confirmation code the import prints is a hash of those bytes, so a test asserts the extracted text is identical before and after the move. The baseline's own text does not contain the list. Plan 1 step 3.3 (run the import on staging) is unaffected if it runs before A6, and uses the new path if it runs after.

## 4. What a plain schema dump misses

Two trials were run. In each, the 287-file database was exported, the export was applied to an empty database, and the result was compared with the snapshot of the original using `scripts/schema-snapshot.mjs --check`.

| Trial | Export | Files of the snapshot that differ |
|---|---|---|
| 1 | `pg_dump --schema-only --no-owner --no-privileges -n public -n private` | **569 of 1,098** |
| 2 | The same but keeping privileges, after first creating `pg_trgm` and the `agent_worker` role by hand | **435 of 1,098** |

Trial 1's 569: 439 function files and 103 table files (permissions, and 13 text-search indexes that could not be built), 13 storage rules missing, 2 sign-in triggers missing, 6 reference tables empty, and the bucket, schema, role, publication, extension and scheduled-job files.

Trial 2's 435 is the important one, because it is what a careful person would do. Every difference left in functions and tables is a permission:

- 308 functions gained `execute` for `anon` (a signed-out visitor), 237 for `authenticated`, 32 for `service_role`.
- 101 tables gained `all` for `anon`, 100 for `authenticated`; the narrower grants they should have had (`select` only, on 41 tables for `authenticated`) were swallowed by the wider one.

The cause: when a role creates an object in `public`, Supabase's default privileges grant `anon`, `authenticated` and `service_role` access at that moment. The migrations then revoke it, object by object. `pg_dump` writes the difference between an object's permissions and Postgres's built-in default, so it writes `revoke … from public` and never `revoke … from anon`. Replayed, the object is created, gets the Supabase grants, and keeps them.

Row-level security still applies to the tables, so this is not every row exposed. It is every function that was closed to members becoming callable, which is the regression plan 2 item A3 exists to prevent, at the scale of the whole database.

**Checked and found empty**, so nothing to carry: custom types, domains and enums (none), aggregates, operators, casts, rules, materialized views, partitioned or inherited tables, foreign tables, extended statistics, text-search configurations, event triggers of ours, collations, role or database settings set by a migration, objects created in `auth`, `storage`, `vault` or `realtime` other than items 5 and 6. The snapshot tool refuses to run if any of these appears later.

## 5. The proof: what "identical" means and how it is shown

### Three kinds of database

| | Built by | Storage and sign-in tables | Used by |
|---|---|---|---|
| **Guard build** | The pinned image, `ci_shim.sql`, files applied as `supabase_admin` | Stand-ins from the shim | `sql-guard`: 157 guards, types check, the A1 snapshot |
| **Stack build** | `supabase start` (CLI 2.116.0), files applied by the CLI as `postgres` | The real ones | The browser suite and the Stripe lane |
| **Hosted** | The migration runner as `postgres` | The real ones | Shared dev, staging, production |

The baseline has to give the same result as the 287 files in the first two, which can each be built twice from nothing. The third cannot be rebuilt on demand; it is compared, not proven (step 4 of the plan, and "what could not be verified" below).

### The comparison, exactly

For the **guard build**, build database **A** from the 287 files and database **B** from the baseline alone, each in its own container (roles are per server, so they cannot share one).

1. **Schema, permissions, jobs, storage, reference rows.** `supabase/schema/` is generated from A (it will already be on `main` from A1, and CI will have confirmed it matches). Then:
   `DRVN_SCHEMA_DATABASE_URL=<B> node scripts/schema-snapshot.mjs --check`
   must print `supabase/schema/ matches the database (… files; …)`. Any difference prints the file and the lines. This covers 525 functions with bodies and permissions, 140 tables with columns in order, constraints, indexes and permissions, 143 policies, 273 triggers, sequences, roles, default privileges, publications, 21 jobs, 8 buckets and the six reference tables.
2. **Everything outside our two schemas.** `psql <A> -f scripts/baseline/outside-catalog.sql` and the same for B, then `diff`. Must be empty. This catches anything a baseline might do to the platform's schemas that the snapshot does not look at.
3. **Rows anywhere.** For every table in `public` and `private`: the row count in B equals the count in A, except `product_grow_runs` (1 in A, 0 in B).
4. **An independent tool.** `pg_dump --schema-only` of A and of B, with owners and privileges, both reduced to a sorted list of statements, then `diff`. Must be empty. This is a second opinion from a tool that shares no code with the snapshot script.
5. **Behaviour.** Against B: `bash scripts/test-sql-guards.sh` (157 guards), `node scripts/generate-database-types.mjs --check` (the generated types file is unchanged), and the snapshot check again afterwards is not expected to pass (guards leave rows) and is not run.

For the **stack build**, the same steps 1 to 4 with two local stacks, one started with the 287 files in `supabase/migrations/` and one with only the baseline. The snapshot tool refuses port 54322 by default, because a stack build differs from a guard build (owner, default privileges, real storage tables); for this comparison it is run with an explicit override against both stacks and the two outputs are compared with each other, not with `supabase/schema/`. Then the full browser suite and the Stripe lane run on the baseline stack. On this Mac two stacks will not fit in memory, so this runs in CI, as a manually started run on the A6 branch.

**The accepted differences, in full.** The comparison is expected to be empty except for these, and each is excluded by construction, not by eye:

| Difference | Why it is not a difference |
|---|---|
| `public.product_grow_runs`: 1 row and its sequence at 1 in A, empty in B | A log line from the migration running the grower once. The hourly job writes the next |
| `cron.job.jobid` values and `cron.jobid_seq` | Counters. Jobs are compared by name, schedule, command and active flag |
| `cron.job_run_details`, `net._http_response`, `public.worker_runs` | Written by jobs running during the build; timing-dependent |
| Clock and random-id columns in reference rows (`updated_at`, `changed_at`, `set_at`, `announced_at`, `agent_controls.id`) | Filled by a default at insert time |
| 5 dropped-column slots in 2 tables | A new table has none. Column order is compared and is the same |

### Each check must be seen to fail (rule R6)

Before the result is trusted, each of these is done to database B on purpose and the comparison must report it: remove one `revoke`; drop one storage rule; drop the `on_auth_user_created` trigger; change one job's schedule; change `payout_hold_days`; delete one reserved name; drop one index; change one line of one function. Eleven such changes were already tried against the snapshot check while building A1 and all were reported; the same list is repeated against the real baseline and recorded.

### Shared dev and staging (step 4 of the plan)

`scripts/schema-snapshot.sql` is now a single read-only `SELECT`, run in a session where every transaction is read-only and the search path is fixed. That was done so it can be pointed at a hosted project without being able to change it. For step 4 it is run against staging and shared dev with a read-only login, and the output is compared with the stack build of the baseline (same role, same real storage tables). Every difference is listed for the orchestrator. Nothing else is done to either database until `APPROVED A6 STEP 5`.

Differences already known from the record, to be confirmed then, not assumed: shared dev's twelve unrecorded history rows (OS id N786) and its extra rows from a rename; a role `os_reader` created by hand on both for the Intelligence OS; the vehicle catalogue and curated generations on shared dev, absent on staging until plan 1 step 3.3; rows in `job_config` (storage origin, payments mode) that the deploy step writes; and any function body that differs because of the five functions overwritten on shared dev that the 10 November review mentions.

## 6. How the baseline will be made

By a script, `scripts/baseline/build-baseline.mjs`, so that it can be reviewed, rerun after A2 and A3 merge, and rerun if the comparison finds a fault. Not by hand. Its output is one file in this order:

1. Session settings, and a header that marks it as a baseline the runner applies only to a database with no tables.
2. Extensions and the `private` schema (item 2, item 11).
3. The `agent_worker` role (item 7).
4. Structure: `pg_dump --schema-only --no-owner --no-privileges` of `public` and `private` from the guard build, with `create schema public` removed. This is the part `pg_dump` is good at: dependency order, exact function bodies, constraints, indexes, comments.
5. Permissions, generated from the catalog (item 1).
6. The objects outside our schemas: 13 storage rules, 2 sign-in triggers, publication membership (items 5, 6, 8).
7. Rows: 8 buckets and the six reference tables (items 4, 9).
8. The 21 scheduled jobs (item 3).
9. Default privileges, as A3 leaves them (item 10).

The generator is checked by the comparison in section 5 and by nothing else: if its output builds a database identical to the 287-file build in both environments, it is right.

## 8. What could not be verified

Stated plainly, so nothing is assumed.

1. **No baseline has been built.** The two trials applied raw exports. The generator in section 6 does not exist yet, and the comparison in section 5 has been run only against those trials and against deliberate changes, never against a real candidate.
2. **Neither shared database has been looked at.** The differences in section 5 are from the written record. The real list will be longer or shorter.
3. **The stack build has not been compared.** Everything measured here is the guard build. Whether the real storage and sign-in tables accept the storage rules and triggers in baseline order is expected (they accept them from the 287 files) and unproven.
4. **A brand-new hosted project has never applied a baseline.** It cannot be rehearsed without creating one, which is Neil's to do. The nearest proof is the stack build plus the staging comparison. The first real proof is the production database itself, so the runbook step that creates it should run the snapshot check, read-only, immediately after the baseline is applied and before anything else.
5. **Whether hosted Supabase lets the migration role change default privileges** is A3's question and is open. It decides item 10.
6. **`pg_dump`'s output order between two databases whose objects were created in a different order** has not been measured. Check 4 in section 5 sorts the statements to avoid depending on it.
7. **The generated types and the 157 guards against a baseline** have not been run. Both read the same catalog the snapshot does, so a pass is expected.
8. ~~Local and CI builds were not compared with each other.~~ **Verified after this draft was first sent.** The snapshot generated on this Mac (arm64) was checked against CI's own database (amd64, the pinned image) by a manually started run on the A1 branch: run 42839710828, `sql-guard` step "Schema snapshot matches migrations", which printed `supabase/schema/ matches the database (1098 files; 525 functions, 140 tables, 143 policies, 273 triggers, 21 scheduled jobs)`.
9. **Dormant behaviour that depends on a row.** The agent's master switch and the settlement settings are carried. If some function reads a row that only exists on shared dev because someone inserted it by hand, the guards would not show it. The row comparison in step 4 is what would.
