# Provider dispute and late-refund recovery

Provider dispute events now enter a private journal keyed by Stripe dispute ID. Open and won/warning-closed basket changes commit atomically. A terminal callback received before its created callback remains terminal. A new provider dispute can reopen an earlier resolved in-app case. A complete, exact-currency basket can enter lost-dispute booking under a five-minute lease; retry verifies its ledger before completing. Expired loss leases appear in worker health. Unknown mappings remain retryable; partial, conflicting or over-50-order baskets create a deduplicated, alerted operator recovery and freeze eligible orders without guessing a full-basket refund.

Late refund failures have two obligations: the buyer still needs the refund, and a previously reversed seller transfer may need repayment. The new verification action reads Stripe; it does not create transfers, issue replacement refunds, or change the accounting allocation. The operator must choose and execute the approved recovery procedure first. Automated replacement initiation/reservation release and multi-transfer allocation remain unfinished. Do not describe this workflow as fully automated or complete.

For an already completed seller recredit, the transfer must match the original seller account, exact owed amount, currency and test/live mode, have an unreversed balance transaction, and have been created after the compensation record. Its metadata must contain the exact `refund_operation_id`, `recredit_adjustment_id` and `refund_reference`. The original reversal is retrieved and checked; an unknown original result requires exact history reconciliation. An uncertain result keeps the case open. A proven zero seller obligation needs no transfer.

Enter the seller transfer ID in the recovery case. Provider verification records immutable, uniquely attributed evidence. A transfer cannot satisfy multiple adjustments. A note or write-off cannot bypass the database closure guard.

Closure also requires exactly one separately settled local replacement refund on the same order/payment, for the failed refund amount, created after the compensation record, with `provider_status = succeeded` and `status = completed`. Its recorded reason must be `Admin refund: Replacement for failed refund <failed Stripe refund ID>`. This explicit linkage prevents an unrelated refund from satisfying the buyer obligation. The normal order refund action prefixes the entered reason with `Admin refund: `. The case stays open if either party's evidence is incomplete; verified seller evidence may already be saved even when closure is refused.

The original failed operation's reservation and any reversal allocation across the original transfer and a new seller recredit need operator reconciliation before a replacement can safely run. This implementation intentionally does not release that reservation or create new money movements as part of case closure. Finish and test that workflow before marking the late-failure remediation checkpoint complete.

Provider fields and retrieval behavior were checked against Stripe's [Transfer object](https://docs.stripe.com/api/transfers/object) and [Retrieve a transfer](https://docs.stripe.com/api/transfers/retrieve) documentation. Local mocks and database guards verify the admission rules; hosted Connect evidence remains a release requirement.
