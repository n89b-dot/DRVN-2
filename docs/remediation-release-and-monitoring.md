# Candidate evidence and independent monitoring

Build a candidate only from a clean committed checkout using `node scripts/release-candidate.mjs build CONFIG.json /outside-checkout/candidate.json`. The configuration must contain exactly: `environmentId`, canonical HTTPS `canonicalOrigin`, `supabaseProjectRef`, `paymentMode: "stripe-test"`, `shippingMode: "stub"` or `"easypost-test"`, boolean `analyticsEnabled` and `searchEnabled`, `betaRequired: true`, and the responsible `operator`. Do not put secrets in this file. Configuration is an operator declaration; hosted observation must confirm it.

The build wrapper binds source SHA, built server/static file hashes, migrations, lockfile and runtime version. Record one report for every gate listed by `REQUIRED_GATES` in the script. Each report needs `gate`, matching `sourceSha`, `buildDigest`, `migrationsDigest`, `environmentId`, `passed: true`, `observedAt`, `evidencePath`, and the evidence file's SHA-256 `evidenceDigest`. Browser evidence additionally requires `counts.expected > 0`, `counts.flaky = 0` and `counts.unexpected = 0`. Keep evidence files beneath the reports JSON directory. Run `node scripts/release-candidate.mjs verify candidate.json reports.json` before promotion. Missing, duplicated, changed, stale (over seven days), future or mismatched evidence blocks promotion. This verifies the evidence package; a reviewer must still assess its contents. No candidate has been promoted by this implementation.

Run the independent monitor on a separately administered runner, outside the DRVN deployment. Supply secrets through its secret store: `DRVN_MONITOR_ORIGIN`, `DRVN_MONITOR_SECRET` (the worker-health bearer), `DRVN_MONITOR_ALERT_URL`, and `DRVN_MONITOR_HEARTBEAT_URL`. Set `DRVN_MONITOR_STATE_FILE` to a persistent writable private file and launch `node scripts/check-worker-health.mjs --watch` under a service manager with restart-on-failure. Default cadence is 60 seconds; `DRVN_MONITOR_INTERVAL_MS` allows 10–120 seconds. Use only one process per state file. Configure the dead-man destination to alert when successful heartbeats stop. The alert receiver must deduplicate `notificationId`, since delivery can succeed even when its response is lost.

The monitor requires every worker family and every inventory job (20261107191000; `docs/production-runbook.md` §9b), names each problem in the alert, pages after `DRVN_MONITOR_CONFIRM_CHECKS` consecutive failures (default 2), re-pages only for a new problem or the 30-minute reminder, honours `DRVN_MONITOR_SILENCE_UNTIL`, rejects stale or malformed health, sends failure/recovery transitions and 30-minute continuing-incident escalations, and sends a healthy heartbeat only after health verification and any required notification. Alert identities are persisted before delivery. Transport failures cannot acknowledge delivery. Test failure, notification outage, runner termination and recovery on the chosen destination before accepting operations readiness. No external destination has been contacted by the local tests.

Exports and package expiry run alongside deletions under the existing five-minute privacy endpoint and its tracked `deletions` family. Any failed subtask fails the family. Queue health includes overdue export jobs and open financial recovery obligations. Future clearing holds and scheduled backoff do not count as overdue work. Ordinary worker freshness budgets remain 30 minutes, saved searches 90 minutes and media 26 hours; a 60-second monitor does not itself establish a five-minute recovery or detection guarantee. Approve tighter budgets and scheduler capacity before claiming that target.

Hosted staging remains unprovisioned: the selected Free organization has no unused active-project slot. Existing projects have not been paused, paid capacity has not been purchased, and no hosted deployment or notification destination is implied by these files.
