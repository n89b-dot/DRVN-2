# DRVN deletion, export and retention inventory

This inventory separates implemented behavior from policy decisions. No statutory retention period is assumed. Financial history, audit evidence, provider retention and original-image cleanup remain release decisions until the responsible owner approves the applicable policy.

| Data family | Export / access | Implemented deletion behavior | Remaining decision or verification |
|---|---|---|---|
| Auth identity, factors and sessions | Own account identity; credentials and factor secrets excluded | Access banned first; hard Auth deletion last; current admin tokens invalidated by recovery epoch | Audited/financial identities can be blocked by immutable foreign keys; approve anonymized retention and operator procedure |
| Public profile, cars, listings, posts and mods | Owned rows, profile/avatar, owned media, fitments, part numbers and hotspots | Profile scrubbed; owned content removed; search changes queued; pending deletion blocks stale writes | Review retained commercial snapshots and any public originals before destruction |
| Car/listing/activity images and avatars | Owned reference rows, paginated | Durable folder/object manifest; inventory before deletion; retained references respected; bounded continuation | Historical original/CDN removal requires approved manifest and provider invalidation procedure |
| Messages, comments, reactions, follows, saves, notifications and reviews | Authored messages/comments/reviews and owned preferences/relationships | Normal FK cleanup after successful identity removal | Decide retention of counterparty conversations and authored evidence |
| Orders, immutable commercial snapshots and payment history | Both sides' authorized order rows and snapshots; explicit safe payment projection | Unfinished orders, payouts, refunds, returns and unresolved capture cases block deletion; financial evidence is preserved | Approve retention reason, duration, access controls and eventual anonymization; raw provider payloads never included in export |
| Returns, disputes, private evidence, seller adjustments, transfers and refund operations | Authorized product views; not all operational rows included in the self-service export | Active obligations block deletion; immutable financial references can require operator handling | Complete policy-specific evidence export/retention; do not treat the current download as a complete legal-subject-access response |
| Product analytics | Current preference exported; no raw external-provider events in download | Explicit browser opt-in plus current account consent; withdrawal stops dispatch; purchase events carry stable IDs | External event erasure/retention requires the configured analytics provider and approved policy. Keep analytics disabled until verified |
| Stripe Customer | Payment credentials stay with Stripe | Verified owned customer deleted idempotently before Auth; customer ID checkpoint survives profile loss | Test connected-account/provider retention and eligible-customer cleanup in the chosen staging account |
| Admin audit, recovery cases and operational logs | Restricted administrator/operator access | Append-only audit and recovery references preserved | Name retention owner and durations; test audit identities are banned and stripped of membership, not erased |
| Backups and object archives | Operator-only access | Local drills use restricted files and isolated targets with worker endpoints disabled | Approve backup retention and RPO/RTO; rehearse coordinated hosted DB/object restore and provider reconciliation |

The self-service export returns an explicit failure if a section cannot be read or exceeds its synchronous capacity. It does not silently truncate at the normal API page limit. Exports use the signed-in RLS client and exclude raw payment payloads, provider secrets and another member's unrelated media.

Deletion manifests preserve the Stripe Customer reference before profile/Auth cascades and record each storage object as pending, deleted or retained. Healthy continuation does not consume the failed-attempt budget. The worker rechecks financial blockers before cleanup and before provider/Auth deletion. A retained immutable FK is an actionable operator case, not permission to disable database protections.
