# Changelog

## 2026-08-01 — Ops: dispute SLA, reporting, dependency security, runbook (Rev E items 12–15)

**Dispute SLA (`0021_dispute_sla.sql`).** Nothing strands: at day 4 a daily pg_cron job (`escalate_stale_disputes()`) notifies both parties the case is flagged for support and stamps `dispute_escalated_at`; at day 10 of seller silence (no refund offer outstanding) the worker pass auto-refunds the buyer through the one refund path — reversal and fee reconciliation included — recorded as `dispute_sla` in the audit trail of the money. An admin or seller acting first naturally prevents both stages.

**Reporting is real.** The prohibited-items policy now has its capability: a quiet "Report this listing/seller" on part sheets and public profiles opens an accessible dialog (labelled reason select, rate-limited, RLS-enforced reporter identity) feeding the console's moderation queue. Verified end-to-end: filed on a listing, appeared in `/admin/reports`, dismissed with a note, audit row written.

**Dependencies.** Next 16.2.9 → 16.2.12, plus `overrides` pinning `sharp` ≥0.35 and `postcss` ≥8.5.18 (the libvips CVEs sat on the user-upload image path). `npm audit`: **0 vulnerabilities**, from 9. The e2e golden-path suite is now a CI job that runs against a dedicated Supabase project when `E2E_SUPABASE_*` secrets are configured, and skips loudly when they aren't.

**Production runbook** ([docs/production-runbook.md](docs/production-runbook.md)): standing up the separate production project, applying and verifying the migration tree, baselining `supabase_migrations.schema_migrations` so the CLI is usable from day one, Stripe live-mode wiring, `job_config` for the scheduled worker, seeding the first admin (SQL-only, MFA), and a quarterly restore rehearsal with a log table — a backup that has never been restored is a hope, not a plan.

**Still deferred, deliberately** (from Rev E's "later" tier): pre-purchase buyer↔seller messaging, category metadata/OG image/structured data, shop profiles, recommendations instrumentation, and the sub-£2 fee-model decision (Stripe's own processing fees remain unmodelled — a pricing decision for the founder, flagged on `/fees` before launch).

## 2026-08-01 — Money correctness: transfers on delivery, reversals everywhere (Rev E items 1–7)

**The clearing window is now real (`0020_transfer_scheduling.sql`).** Transfers no longer fire inside `payment_intent.succeeded` — the webhook records a `transfer_intents` row; buyer-confirmed delivery stamps `available_at = delivered_at + 7 days` (the exact window the ledger has always displayed); pg_cron's `drvn-transfer-worker` marks due intents ready in pure SQL — only while the order is in a deliverable end state, so a dispute freezes the money by construction — and the worker (`src/lib/payments/transfer-worker.ts`, reached via `/api/jobs/transfers` behind `CRON_SECRET`, or the console's Payments → "Run worker now") turns them into Stripe transfers. The Stripe idempotency key stays `transfer:{order_id}`, the same key the legacy path used, so nothing historic can duplicate. Backfill created intents for every captured-but-untransferred order: sellers who sold before onboarding are now `blocked_unpayable` rows the console can see and the worker retries forever (attempts don't increment on the wait state), unblocked eagerly when `account.updated` reports them payable. Stub-era orders were cancelled on record.

**Every refund path reverses the seller's transfer.** Buyer-accepts and seller-cancellation migrated onto `refundOrder`; a lost card dispute books through the new `recordExternalRefund` (the chargeback already took the platform's money — the seller's share is now reclaimed proportionally instead of silently absorbed); dashboard refunds arriving on `charge.refunded` attribute via our refund metadata first, exact-amount fallback second, and anything ambiguous opens a `payment_recoveries` case instead of leaving the order quietly `paid` and double-refundable. Both share one effects core: proportional reversal (cumulative-deterministic keys, so overlapping paths can't double-reverse), fee reconciliation, intent cancellation, recovery on failure.

**Webhook `event.id` dedup** — every event is claimed in `webhook_events` before handling; a fully processed id acknowledges immediately, a crashed first pass reprocesses (handlers are idempotent). **Alerting** — the settlement lines that used to be money-losing log statements now produce recovery cases or blocked intents that stand in an admin queue until a human closes them, alongside the existing Sentry forwarding.

## 2026-08-01 — Admin console: the intervention path (Rev E, Task 1)

DRVN previously had no admin concept at all — no way to force a refund, resolve a stuck dispute, take down a listing, or suspend a seller. This adds the full back-office, gated and audited, in Livesheet's visual language.

**Schema (`0018_admin.sql`, `0019_money_infra.sql`, both applied live and verified).** Admin membership is a separate `admin_users` table with no client-reachable grant or policy — deliberately *not* a flag on `profiles`, whose self-update policy has already been one live money-extraction path (0017). `public.is_admin()` (`stable security definer`, false for null-uid contexts) is used **inside RLS policies** on orders, order items, payments, offers, messages and listings, so the database grants admin visibility declaratively. `admin_audit_log` is append-only for every role including service_role (trigger-enforced). `reports` gives moderation a substrate; listings gained a seller-unwritable `removed` status and profiles gained service-role-only suspension columns, with suspension enforced in the listings SELECT policy (a suspended seller's stock leaves browse; new listings are refused). 0019 adds the money plumbing the refund path and the Rev E money work share: `webhook_events` (event.id dedup), `transfer_intents` (persisted before Stripe is called; doubles as the stuck-funds queue, with `available_at` modelling delivery + clearing hold), `payment_recoveries` (failed reversals and unattributed partials stay open until a human closes them), and explicit refund-adjustment columns on orders (`refunded_cents`, `platform_fee_refunded_cents`) so checkout figures stay frozen and derived numbers subtract. Verified by impersonating a real `authenticated` user — 23 assertions in `supabase/tests/admin_guard.sql`, now also run in CI.

**The one refund path (`src/lib/payments/refunds.ts`).** Built once, correctly, with the admin force-refund as its first caller (the other Rev E paths migrate onto it next): reverses the seller's transfer proportionally via `transfers.createReversal` (separate charges and transfers — `reverse_transfer` doesn't apply), uses per-**order**, cumulative-amount-deterministic idempotency keys (per-intent keys collided across a multi-seller basket's orders — Rev E item 3, fixed at the provider seam), reconciles the platform fee's share of every refund, stamps `order_id` metadata on the refund so the webhook can attribute it, claims the order atomically before any money moves, and records a failed reversal as an open `payment_recoveries` case — negative-balance recovery, not a log line.

**Console (`src/app/(admin)` at `/admin`).** Gated by `getAdminContext()` → real 404 for non-admins (metadata resolved conditionally so even the tab title doesn't confirm the route exists); out of nav and sitemap; every server action re-verifies membership and writes its audit row in the same code path (`auditedAction` — no mutation without an audit entry, reason required). Surfaces: **Overview** (needs-attention KPI deck), **Disputes** (oldest-first queue, over-SLA flagging at 4 days), **order sheet** (money state, dispute block, both parties with history, thread, force refund full/partial + resolve-for-seller), **Orders** (search by id / `pi_…` / username), **Listings** (takedown with seller-visible reason, restore-as-paused), **Users** (suspend/unsuspend; suspension pauses exactly the live stock and unsuspension restores exactly that set), **Reports** (moderation queue), **Payments ops** (recovery cases, transfer pipeline / stuck funds, webhook stream), **Audit** (filterable, append-only). Admin data access lives in `src/lib/admin/` with no imports from the product routes, so the group can later lift onto a subdomain behind Cloudflare Access without a rewrite. Verified end-to-end in the browser: non-admin 404, dispute queue, resolve-for-seller action (audit row written, order restored, both parties notified).

## 2026-07-26 — Production remediation: security, atomic checkout, and the missing journeys

Implements the remediation plan in [`docs/production-readiness-report-v2.md`](docs/production-readiness-report-v2.md) §9, phases R0–R5 and R7. **R6 (real payments / Stripe Connect) is deliberately not included** — payments still run on the stub provider, and checkout is labelled test mode throughout.

**Security (migration `0006_security_hardening.sql`).** RLS — not the server actions — is the real boundary, because the anon key plus a user JWT reaches PostgREST directly. Closed: the forged-order chain (the `orders` INSERT policy checked only `buyer_id`, so a raw request could mint a `paid` order naming any victim as seller, which the review policy then accepted as proof of a trade — the client INSERT policy is now dropped entirely and reviews must match a real order's counterparty); `profile_type` self-escalation to `shop`; ownership reassignment on cars, listings and activity posts (no owner-update policy had a `WITH CHECK`, and `USING` is evaluated against the old row); offer tampering; comment and reaction visibility, which `0003` shipped as `using (true)` and so exposed engagement on unpublished and private-car posts. Added text/amount bounds, storage MIME and size limits, and a DB-backed rate limiter. Also: fail-closed proxy, `//` open-redirect fix, env validation at boot, `httpOnly` cart cookie, `source_car_id` ownership check, and stored-URL validation.

**Commerce (`0007_commerce_lifecycle.sql`).** Replaced check-then-act with claim → pay → finalize. `purchase_begin` uses a conditional `UPDATE` as its lock, so two buyers can no longer be sold the same part, and returns per-item outcomes; `purchase_finalize` settles or releases. Payments are now persisted with a provider reference and idempotency key. Order lifecycle gained shipping address, carrier and tracking, and the `shipped`/`delivered`/`disputed` states that were declared and unreachable. Parties are anonymised on account deletion rather than cascaded, so erasure no longer fails on a foreign key. Currency is threaded through; one order per seller *per currency*.

**Journeys.** `/orders/[id]` order detail with a status pipeline; dispatch with required tracking; mark-received; cancel with refund; post-sale messaging keyed to the order so buy-now purchases have a channel. `/listings/[id]/edit` and a seller console at `/listings` with drafts, pause, end and delete — listings were immutable after publishing. Activity posts gained edit and delete. Account basics: change email, change password, forgot/reset, delete account. A real checkout step collecting a delivery address, with seller-set flat shipping and the per-seller split shown before paying. Seller profiles now show listings, reviews, rating and sales count. Onboarding is enforced on the email/password path, which previously left those accounts with `username = NULL` forever.

**Car sheet.** Activity is a real tab again: `SheetTabs` provides genuine `role="tablist"` panel switching with keyboard support and URL-backed `?view=` state, so a car's activity is deep-linkable and still server-rendered. The sheet now queries listings for the first time — a "For sale" panel of parts released from that car, per-build-line release actions, `/sell?car=&mod=` pre-fill, and `mod_items.linked_listing_id` finally written.

**Shell and hygiene.** The landing page's navigation was invisible below 980px (a hand-rolled header using `display:none` links); it now uses the real signed-out bar. Added loading/error/not-found boundaries where there were none, SEO metadata with OpenGraph plus `sitemap.ts` and `robots.ts`, image optimisation, security headers including CSP, Terms/Privacy/Fees pages, a proper modal primitive with focus trap, notifications as a real table with unread state, marketplace pagination and sort, and Vitest with CI. Removed ~5,700 LOC of dead weight: `/mockup`, the three landing concepts, pre-Livesheet concept CSS, the legacy component shim, and the `drvn-data` seed fixtures the landing page was presenting as live content.

**Taste-note correction.** `design-mockups/LEDGER.md` recorded "too blocky" as a rejection of pill tabs and generalised it into a preference for jump-links over segmented controls. That reading was wrong — the objection was to corner radius only — and it is what removed the car sheet's tabs. Corrected, with a note to record objections literally rather than inferring principles from them.

## 2026-07-16 — Product framing clarification: marketplace first, provenance as supporting feature

- Clarified the core product thesis across documentation: **DRVN is a marketplace for parts from modified cars** — selection, easy listing, easy buying, and enthusiast identity are the point. The car profile's provenance/trust-context layer (source car, seller credibility, fitment, pairing history) is a **supporting differentiator, not the mission**, and must not be treated as the product's headline in design, copy, or roadmap decisions. Earlier framings over-weighted this layer as "the reason to exist," which had been steering design explorations toward documentation/provenance-centric concepts.
- Updated: `docs/DRVN-PRD-v3.1.md` §3 (Core Product Thesis, now marked *clarified 07.2026*), `docs/product-overview.md` ("What we're trying to create"), and `design-mockups/LEDGER.md` (Product context + diagnosis note) so future design-exploration runs center the marketplace experience rather than provenance. No app code or existing concepts changed.
