# Changelog

## 2026-10-21 — The agent foundation (A2), invisible to members

Everything the agent needs to act, and nothing that acts yet: the agent is paused for everyone by a kill switch until the A3a beta.
- **Data.** Mandates (every version kept), tasks, an append-only record of decisions and moves, chat, approvals and a job queue, each owner-only, in the member's export (v10), removed on account deletion, and kept for the periods Neil ruled.
- **Who it acts for.** A separate database role, `agent_worker`, that can't read a table. Every move it makes needs a job it leased; the database then works out the owner and re-checks their side, suspension, limits, the mandate and the kill switches. Its moves go through the same negotiation path people use, and each round records that the agent made it.
- **The minimum.** An agent's minimum can only make the listing's floor stricter, never lower.
- **Rules decide money.** `negotiate.ts` picks every amount from the owner's limits and the offer history. The seller's agent never accepts by itself; it asks its owner. Property tests and seeded simulations (seller's agent vs a person, buyer's agent vs a person, agent vs agent) run in the unit suite, and the same three run through the real worker role in `tests/operations/agent-worker.test.ts`.
- **Admin.** `/admin/agent` pauses all, one side, one member's agent, one mandate, one listing or one account, audited; offers and orders already made are untouched. Health counts go to monitoring.
- **The model.** `src/lib/ai/` and a tool-runner turn with read-only tools, redaction and untrusted-data wrapping, plus an eval fixture suite. No member reaches the model until A3c.

## 2026-10-20 — Car generations (graph foundation, B1 step one)

Cars now know their generation. `vehicle_generations` holds each generation of a catalog model — `Mk8`, `E46`, `R34`, `ND` — with its platform code and years, seeded by hand with about 200 enthusiast generations (no open source carries them). A car resolves to one only when exactly one generation of its model covers its year; changeover years, such as a 2020 Golf R that could be a Mk7 or a Mk8, resolve to nothing so the owner can be asked, and an owner's choice is kept while it still fits. Nothing a shopper sees changes: vehicle fit and search don't read generations yet. Explore's build search was restated to carry the two new car columns.

## 2026-10-18 — Show my minimum, one lock order, and negotiation drills (negotiation v2, step three)

- **Show my minimum (O-3).** Sellers choose whether buyers see "offers accepted from" their minimum, and it's off by default. The amount stays private; the listing page asks for it only when the seller has turned it on (`listing_public_offer_floor`).
- **One lock order.** Checkout freeze, seller cancellation, payment finalisation and their callers now lock the listing first, like acceptance does. Every path that sells a listing takes listing → offer → order → payment, so a checkout racing an offer move waits instead of deadlocking.
- **Drills.** `tests/operations/negotiation-concurrency.test.ts` races two counters, an acceptance against a pass, a checkout against a cancellation, and an acceptance against another buyer's checkout. Each time, one wins and the other is told why. `e2e/negotiation-three-rounds.spec.ts` plays a full five-move deal in two signed-in browsers.

## 2026-10-17 — Negotiation v2: counter-backs for everyone (step two)

Buyers can now counter back. Every move goes through one database function, `offer_move` (or `offer_open` for the first offer), under the rules in `docs/decisions/negotiation-v2.md`:
- turns alternate;
- a buyer has 3 offers per part, counter-backs included, across every thread; offers already live count as the first;
- the seller's counter stays above the offer, within the asking price and at or above their minimum;
- each move gets a fresh 72 hours;
- an offer below the minimum is recorded as declined and uses one of the 3, so the minimum can't be found by trial and error; the seller sees "declined automatically";
- retrying a move after a lost response replays it, and a move made against an out-of-date offer is refused.

Sellers can no longer cancel an accepted offer's order once the buyer has started checkout. New notifications: the buyer countered back (to the seller), and an offer expired (to both).

In the app:
- the offer box and the offer page offer "Counter back" with "N of 3 offers left";
- the copy says how the rules work;
- a buyer whose 24-hour checkout ran out is told the offer lapsed, rather than that it was "already settled".

The old offer paths still work until the new app runs everywhere; a later step removes them.

## 2026-10-17 — Every offer move is recorded (negotiation v2, step one)

Each proposal's minimum at the time is kept privately in `offer_round_terms`. Today's offer code is unchanged; a trigger records its moves, and a backfill rebuilds the history of every existing offer. The offer page now reads its history from the rounds, falling back to the old reading if they can't be read. Members' exports include their rounds (contract `2026-10-17.v7`). The design for the rest of negotiation v2 is `docs/decisions/negotiation-v2.md`.

## 2026-10-17 — Row security checks "who is this?" once per query

Postgres ran `auth.uid()` once per row in 88 of the 115 row-security policies, and `is_admin()`, a table read, in 34 of them. Migration `20261017140000` wraps each call in `(select …)`, so it runs once per query. Who can read or write what is unchanged: every policy is its original apart from the wrapping, and all SQL guards pass. The new `rls_initplan_guard.sql` keeps new policies in this form. ## 2026-10-17 — The offer minimum is private

A seller's lowest acceptable offer was stored on the listing, which anyone could read through the database API. It now lives in `listing_private_terms`, which no member or visitor can read; the seller reads their own through `my_listing_offer_floor`. This is A0's first rollout in the agent plan, in three steps.

- **Step one, expand** (`20261017120000`, on shared dev): the private table, a copy of every minimum, and a trigger that kept the copy in step. Nothing read it yet.
- **Step two, switch** (`20261017130000`, `20261017130100`):
    - The old column is emptied and must stay empty. Any write that still sets it (the sell and edit functions, an older app build, a script) is moved into the private table by a trigger.
    - "Minimum no higher than the price" is checked from both sides: a minimum set above the price is refused, and so is a price cut below the minimum.
    - Offers below the minimum are refused by a trigger that reads the private table. The message no longer names the amount: "That's lower than the seller will accept."
    - The edit page reads the minimum through the seller's own function and refuses to open if that read fails, so a save can't silently clear it.
    - The export contract is now `2026-10-17.v6`, with a `listing_private_terms` section. Deleting an account clears the member's minimums.
- **Visible change:** buyers no longer see "Offers accepted from $X" on a listing or in the offer box. The PRD (O-3) makes showing it the seller's choice, off by default; that toggle comes with negotiation v2.
- **Step three, contract** (later, once the switched app is live everywhere): drop `listings.offer_floor_cents` and the step-two trigger, and have the sell and edit functions write the private table directly.
- Guard `offer_floor_privacy_guard.sql` (28 checks); `security_guard.sql` 4b now expects the new refusal.
- **Search-path guard** (`function_search_path_guard.sql`, the advisor follow-up): every SECURITY DEFINER function must pin its `search_path`, and all 194 already do. The advisor's 10 flagged functions stay unpinned on purpose. They are caller's-rights SQL functions the planner inlines, and a `SET` clause would stop the inlining the 2M-scale search plans rely on. They are now a reviewed list, and any new unpinned function fails the guard.
- **Signed-in definer functions reviewed.** `definer_exposure_guard.sql` already listed the SECURITY DEFINER functions a visitor can call. It now also lists the 21 that only signed-in members can call, each with the reason it is safe: every one answers or acts only for the caller, or refuses anyone but an admin. A new one fails the guard until it is reviewed.

## 2026-10-04 — Performance: a shared cache for signed-out visitors, and search that works at volume

Two pieces of the performance work that needed no hosting: caching public data, and checking query plans against realistic volume.

- **Signed-out visitors read a shared copy.** The marketplace, Explore, and listing, car, post and profile pages read through one shared copy of public data for anyone not signed in (`getPublicPageClient`, `src/lib/supabase/public-cache.ts`). A copy is never shown past 60 seconds — Next's own cache serves an expired copy once more while it refreshes, which on a quiet page can be hours old, so an expired copy is discarded and the database asked. Only reads go in: a table read, or a function on a named read-only list; a write always reaches the database. Members always read live. Typed searches and price ranges stay live. Off in development, on the e2e stack and with `DRVN_PUBLIC_CACHE=off`.
- **Writes clear it.** Every action imports `revalidatePath` from `src/lib/revalidate.ts`, which also clears the copy for the kind of thing the page shows; a test fails the build on a direct import from `next/cache`. The Stripe webhook, the reservation-expiry worker and the account-deletion job clear it too.
- **Search at volume.** Seeded to about 100× the beta, every text search on Explore and the marketplace hit the 3-second limit and failed, and "search updates" took two minutes when allowed to finish. Migration `20261010100100` makes search read through trigram indexes and lets the planner read a page off an index; the app sends searches to new entry points and pages the Explore wall through `feed_event_page`, falling back to the old functions until the migration is applied. Results are unchanged, row for row. Before/after and what is still slow: `docs/performance/query-plans.md`. Reproduce with `scripts/perf/`.
- **Read rules.** The policies on parts, cars and part photos asked "is this member suspended?" with a function call per row; they now ask once per query (`20261010095900`, `suspended_profile_ids()`). Who can see what is unchanged. At volume a marketplace page with its count went from 653 ms to 77 ms and the Explore wall from 101 ms to 11 ms.
- **Listing page.** The "updates that tagged this part" read timed out at volume and held the page for three seconds on every view; it now reads from the tag rows (indexed by part). The view counter was never sent — a Supabase query does nothing until awaited, and it was called with a bare `void` — so no look had ever been counted; it is sent now, for members only (the function refuses signed-out callers).
- **Marketplace count.** An unfiltered marketplace view takes its total from the category counts already on the page instead of counting every part again.

## 2026-09-25 — Facebook importer: the linked listing's own price, photos and link

A live test against real Marketplace listings found the Facebook adapter drafting a different price on every run ($25, $30, $25 for a $200 exhaust) and sometimes a stranger's title ("Royal Court Estelle Blush Boudoir Pillow"). A logged-out item page embeds ~20 recommended listings with the same keys, ahead of the linked one, and the adapter took the first match. Its test page was invented, so the tests passed.

- **Currency.** A non-USD price (Facebook's declared currency, or £/€/A$/C$… in pasted text) is left unset with a review note naming it; `foreignPrice` in `extract/validate.ts`, and the AI prompt says the same.

- **Removed listings** fail as `source_listing_gone` ("That listing isn't available any more…"), with paste offered, instead of "needs a login"; the Facebook outcome aggregate records them as `listing_gone`.

## 2026-09-19 — Local, and a default lowest offer (WS15, P-9)

Cars are a local hobby. The person with the part you need is usually forty minutes away, and nothing in the product knew that: DRVN stored a free-text `location` and did nothing with it. `profiles` now carries a **country** and a **region** from a curated list ([`regions.ts`](src/lib/geo/regions.ts)), settings asks for them, and Home grows a **Local** tab.

It is coarse on purpose — a country and a region, never a town. A public build sheet plus a town is close enough to an address, and the PRD rules location tags out. A country with no regions listed is fine; Local then works at country level, which is the right grain for a small market. The tab appears only once a member has said where they are; nothing is inferred from an IP address or a phone.

Local is `local_feed_rows` — the same timeline with one more filter — rather than a second view, and `feed_events` gained an `owner_id` so it could be asked "whose is this" at all. Two views over the same union would have drifted within a month.

Alongside it, **P-9**: `profiles.default_offer_floor_pct` prefills the sell form's lowest acceptable offer. It is a default and nothing more — changing it cannot retroactively change a listing a buyer is already looking at.

## 2026-09-19 — Posting without a car (WS14b)

Principle 1 of the direction says the car gives context and is never a gate. `activity_posts.car_id` was NOT NULL, so a member who had sold their car — or who was selling parts before buying one — could not post at all. It is nullable now, and the rule that replaces it is enforced in the database rather than in the composer: **a post must be about a car, a tagged part, or both.**

Dropping the constraint was the easy half. Every reader, the writer and the RLS policies expressed "has a car" as a join or an EXISTS against `cars`, and each of them would have dropped a carless post **silently** — which to the member is indistinguishable from posting into nothing. So: `feed_events` and `local_feed_rows` admit carless updates, `search_update_ids` joins outer, `write_activity_post` accepts a null car in quick mode, and the select and insert policies on `activity_posts`, the shared `activity_post_visible()` and the `activity_images` policy were restated for a post whose subject is a part. Restated, not widened: you still must own any car you name, and drafts stay author-only. A *published* post with no car is public because there is no private car to hide behind and publishing is the act of making it public.

The worst of the silent failures was notifications. `notify_on_save`, `notify_on_activity_comment` and `notify_on_activity_reaction` each built the permalink by hand as `'/cars/' || slug || '/activity/' || id`. With no car the join found nothing, the owner stayed null, and the save or comment worked while the author was never told. All three now call `post_href()`, the SQL twin of [`postHref()`](src/lib/activity/href.ts) — one answer in two languages, instead of thirteen hand-built copies of a string and thirteen chances to emit `/cars//activity/`.

A carless post lives at `/posts/[postId]`, with its own share card and its own shape: there is no build to sit inside, no breadcrumb back to a car, and the parts it tagged are the subject rather than a footnote under the photos. A post that *does* have a car redirects to its car URL — one canonical address per post, because two would split the share links and every link already in the world points at the car one.

[`carless_post_reach_guard.sql`](supabase/tests/carless_post_reach_guard.sql) is the proof: a carless post publishes, one about neither a car nor a part is refused, it appears in the timeline with the right owner, search finds it, Local finds it in the author's region and not in another, and a save, a comment and a reaction each reach the author at the right URL.

## 2026-09-19 — Quick post, the photo rule, tagging a part (WS14a)

Posting meant the full editor: a required title, blocks, autosave, a draft. "New wheels turned up" had nowhere to go. The quick box is photos, a caption, Post — and `activity_posts.title` is nullable, because generating *"Update from the Silvia"* would be writing DRVN's sentence on somebody's behalf. Every reader now goes through [`postHeadline()`](src/lib/activity/headline.ts), which falls back to the member's own first line and only then to a neutral label; a dozen readers each inventing their own answer is how one surface ends up saying "Untitled" while another shows a blank heading.

**A quick post never touches a saved draft.** This is the release-blocking contract, and it needed a new write mode to hold: `publish` converts a car's existing unpublished draft *into* the published post, so without a separate path somebody halfway through a long update who fired off a photo and a caption would have found the long one gone and its text replaced. `quick` returns before the draft lookup ever runs, and [`activity_quick_post_guard.sql`](supabase/tests/activity_quick_post_guard.sql) asserts the draft is byte-identical afterwards. The handoff is the other half: with no draft, "Write a full update" carries the caption over; with one, the link says "Continue your draft" and nothing is merged, because merging two pieces of somebody's writing is not a thing software should do.

Every **new** publish needs a photo — both things a post can be about are physical. Drafts are exempt, and so is editing an already-published post, so a post from before the rule can still be fixed.

A post can **tag up to three of the author's own active parts**. Only their own, because a post is a place to say "this is for sale", not a place to advertise somebody else's stock — and `sync_activity_post_listings` is SECURITY DEFINER, so it checks the author itself rather than trusting the caller. Three at most: a post with eight parts tagged has stopped being an update and become a shop window.

Trending models and builders worth following are woven into the wall, and a breaker renders **only with at least three results**: two builders is not a section. Legacy posts with no photo are left off the photo walls rather than borrowed a car's cover, and stay everywhere else.

The seller KPIs moved to `/selling`, where somebody goes to run a shop. Empty tiles don't render, a member with no car is offered "Add your car" instead of an empty garage tile, and with fewer than three posts the first rail card follows the last post rather than sitting alone in a column.

**The garage** listed every car as a sheet, so one car read as a list of one and six read as six half-sheets you could work on none of. A switcher picks the car; the focused view gives it a stat strip and tabs — Overview, Mods, Parts, Media — mounting the editors that already existed. `?car=` drives it, so the view is linkable and the back button works.

## 2026-09-19 — Profile & Store (WS10)

A profile was About / For sale / Reviews / Activity — a seller's page with some cars attached. It is now **Overview · Garage · Updates · Parts · Reviews**: a person with a garage, whose parts happen to be for sale. Same content, opposite emphasis, and it matches how the rest of the product is now organised. The old `?view=` keys still resolve, because those links are in messages and bookmarks and renaming a tab isn't a good enough reason to break them. The About tab is gone: a bio is one paragraph, and giving it a whole tab meant the first thing on somebody's profile was prose rather than their cars.

**Parts is the store.** The same marketplace grid and the same card, filtered to one seller — a part shouldn't look like a different object because of which page it's on. It runs its own rows query rather than the marketplace's, for one reason: the store shows **sold** parts and the marketplace never does, and bending the marketplace query to carry a seller key would put owner-visible state one URL parameter away from every public browse surface. Everything after retrieval is shared.

Which statuses a store shows is decided by **who is looking, never by the URL** ([`visible-statuses.ts`](src/lib/store/visible-statuses.ts)). Public sees active and sold; the owner also sees draft, paused and reserved. The tab a visitor picks can only ever narrow their own allowance, so `?status=draft` on somebody else's store stays active-and-sold rather than listing their unpublished work. Seller and status filter *inside* the query, before the count and the page window — filtering after fetching gives a count that disagrees with the rows and a silently short last page. The owner sees an edit link where a stranger sees add-to-cart.

The header gained a banner, borrowed from a car's cover so it is never a separate upload, plus followers and cars. `profiles.store_note` is one short line pinned above the grid — capped at 180 characters in the database, because it is voice, not policy, and policy belongs in the returns and shipping settings where it's enforceable.

## 2026-09-19 — Marketplace and its card (WS9)

The most common way people describe a part is by who made it — "Öhlins coilovers", "Brembo calipers" — and brand existed only inside the free-text title, so it couldn't be filtered. `listings` gains **brand**, **part_miles** and **part_miles_unit**, brand joins the filters, the facet, the listing search text and saved searches, and a conservative backfill matches the same curated brand list the build sheet's parser uses.

**The card.** Brand, a title clamped to two lines, price, delivery, condition with miles on the part, compatibility, one line of the seller's own description, their avatar with "N for sale", "Off my {car}", and add-to-cart. No seller rating — M-5 rules it off the browse card, because a score there invites comparing people rather than parts; it stays on the item page. No Buy now — deciding to buy happens on the item page. The description line is the seller's own first sentence, never a generated summary: a card that paraphrases is a card that can be wrong about somebody else's part.

**The phone column is two across again.** The design proof measured why it couldn't be: 163.5px columns, 523–571px cards, titles running to six lines because nothing clamped them. The clamp came first and the column followed. Below 340px it drops back to one — at 320px the columns are 146px and the price and the cart square start fighting for the same row.

Two things were easy to get silently wrong and are now explicit. `save_listing_creation` enumerates its columns in **three** places — insert list, values parser, replay-drift comparison — and all three moved together; missing one drops the field on publish while everything else looks correct. And `brand` joined `SAVED_SEARCH_KEYS`, because without it a saved search drops the brand and the alert job, which runs the same query, mails the member about every coilover on the site.

The desktop filter panel now renders inline rather than as a sheet from 1024px, through a new `inlineFrom="lg"` on `BottomSheet` — one set of fields in two presentations. Its placement as a genuine left column is still to do: the panel and the results sit in different subtrees, so that needs `page-content` restructured around a sidebar slot.

## 2026-09-19 — Add what you bought to your car (WS4)

The third loop, and the one that was a dead end: a part arrived, went on the car, and the build sheet knew nothing about it. A delivered or completed order now offers **Add to a car**, per item — an order can hold several parts and they may not all be going on the same car.

The mod line is built from `order_items.commercial_snapshot` (0049), **never the live listing**. That is the whole point: by the time somebody actually fits a part, the seller may have edited the listing, re-shot it, relisted it as something else or deleted it outright. What goes on the build sheet has to be what was actually bought.

It is idempotent through the unique `mod_items.source_order_item_id`, and a second tap answers *"That part is already on this car"* rather than erroring or duplicating — the same answer either way, which is what idempotent should feel like. Buyer, car ownership and order state are all checked server-side; "arrived" means delivered or completed, the same window the review and return flows use.

**The provenance line is not written into the mod's text.** `source_order_item_id` is the durable fact, and the source car is read back from the frozen snapshot at render time where its *current* visibility can be checked — a sentence written once into `raw_text` can't stop naming a build that later went private. A public source build is named and linked; a private one isn't named at all, the same rule every other source-car mention follows.

The reverse category map answers `null` rather than guessing. "Engine" could be a turbo, a manifold or a whole long block, and a wrong category quietly mis-files the part on somebody's build sheet — while no category is an ordinary state for a hand-typed line anyway.

## 2026-09-19 — Main car (WS5)

Four surfaces sorted a member's cars and none of them agreed: created ascending in the garage, model year descending on the profile, whatever the query happened to return on the sell form. Somebody with four cars saw a different "first" car depending where they were standing, and never got to say which one they actually meant.

`profiles.main_car_id` is that answer, set from the car's own settings. It drives the featured car, the default profile banner, car order everywhere, the Garage's focused view and the first one-tap suggestion in the marketplace vehicle picker. One helper ([`lib/cars/order.ts`](src/lib/cars/order.ts)) replaced all four sorts, and **null stays the ordinary state** — with no main car every surface falls back to newest-first, exactly as before, so nothing changes until somebody chooses.

**Offered, never applied.** The marketplace shows "Parts for my {car}" as a one-tap choice and nothing more. Defaulting the filter would be easy to call helpful and isn't: a marketplace that silently hides most of its stock the moment you sign in looks empty, and the visitor has no idea why. An explicit or URL-supplied vehicle always wins, and a cleared filter stays cleared — clearing is an answer, not an absence.

The banner is chosen from photos that already exist, so it is never a setup step: the main car's cover if that car is public and has one, otherwise another public car's, otherwise no banner at all. A private car's cover is never borrowed — the owner kept that car back, and a public profile isn't the place to publish its photo. `ProfileHeader` gained `bannerUrl`, `stats` and `location`; the scrim is a gradient so the photo still reads as a photo at the top while the name stays legible at the bottom.

Ownership is enforced by a trigger, not by RLS: RLS says who may update the profile row and nothing about whether the *value* is theirs, so without it a member could feature somebody else's car. `security_guard.sql` covers it.

## 2026-09-19 — A listing reaches the people following you (WS3)

The second of the three loops. The followed feed carried cars and build updates only — a followed seller's new listing showed up nowhere, because `follows` has no seller-listing edge and the feed never asked the listings table. Now a new listing reaches anyone following that seller **or** the car the part came off, which is the whole argument for the community and the marketplace being one product rather than two.

Two queries feed it rather than one `or`: only the seller lane can use the new `(seller_id, status, created_at desc)` index, and an `or` across both lanes would give up the index for the half that has one. The same index also serves the Store tab and the "N for sale" count that WS9 and WS10 will need.

Everything hard about B-1 is in [`feed-merge.ts`](src/lib/feed-merge.ts), pure and tested without a database. **A listing appears once however it's followed** — follow the seller and the car and you followed two things, not two listings. **Order is stable across pages**, because paging slices this list and equal timestamps are ordinary (a bulk insert stamps rows together); the id is the tie-break, arbitrary but total, so page one and page two can't disagree and show a card twice or skip it. **At most three of one seller's listings sit together** — the fourth waits for somebody else and then comes straight back, so a seller who lists eight wheels at once stops owning the top of the feed without losing anything.

## 2026-09-19 — Add a part by pasting a link (WS6)

A build sheet was a typing exercise, and a sheet nobody fills in can't make the parts that come off it sellable with provenance. "Add mod" now opens on a product link: one fetch fills the title, brand, part number, category, a thumbnail and what the shop was charging, and everything stays editable. Typing stays first-class — a failed fetch falls back to it with a sentence, never an error page — and the public build page shows the thumbnail with a plain link out.

It is the [listing importer](docs/site/listing-import.md)'s plumbing at a fraction of its weight: the same SSRF guard, pinned DNS, byte caps and sharp re-encode, and none of the job ladder, AI extraction or twelve-photo gallery. `extractJsonLdProduct` learned to read schema.org `brand` (both the bare-string and Organization-node shapes), and the image importer's bucket and path are now parameters.

**Two rules are structural rather than promised.** A shop's product photo can never become a listing photo (L-4): the thumbnail is uploaded to `car-images`, not `listing-images`, and the sell prefill does not select `image_url` at all — a test asserts that projection, so widening it has to be deliberate. And a reference price without a currency is not shown, stored or returned, because the database refuses the half-state and a bare number reads as pounds to one person and dollars to the next. Prices are refused rather than guessed: `1.299,00` is ambiguous against a thousands comma, so both forms are read as no price. Writing that test caught a real bug — a stripped minus sign made `-40` parse as £40.

`RATE_LIMITS.fetchPartLink` is 30/hour, looser than the importer's 10, because one page fetch and one thumbnail is cheap and somebody filling in a sheet in one sitting pastes a lot of links. `mod_items.image_url` joined the media lifecycle's reference check — without it the 48-hour sweep would take the thumbnail back out from under a build sheet still showing it. A link-added part renders as an `ObjectRow` on the public sheet (it has a picture and somewhere to go); a typed line stays a ruled `DataRow`.

## 2026-09-19 — Change a part: removal is a state (WS2)

The first of the product's three loops, and the one that was quietly destroying its own evidence. A modification line used to exist only while the part was on the car: the editor dropped the row, `save_mod_items` deleted anything the payload omitted, and the part was gone — along with the fact that it had ever been fitted, and along with the provenance behind any listing released off it. People also typed over rows to record a replacement, which silently rewrote what past updates and live listings referred to.

**`mod_items` gains `status` (installed / removed) and `removed_at`** ([migration](supabase/migrations/20260919170000_mod_record_identity.sql), applied to the shared dev project and the local test database). **Remove** keeps the row's id and marks it. **Replace** is its own editor action — the old line is marked removed and keeps its id, a fresh line takes its position. **Editing in place** stays what it always was: a fix for typos. **Delete** is still "omit the row", and is only offered on a line with no linked listing. Removing now asks inline, in the row: *What happens to the old part?* → **List it** · **Just remove it** — and neither answer loses the record. "List it" commits the sheet *before* opening the sell form, so abandoning the form leaves the part under "Came off this car" rather than losing the removal as well as the listing.

The parts that came off get their own section, in the editor and on the public build sheet, each still carrying its listing or the owner's way to make one. That is what makes a used part's provenance checkable: a buyer can read the build a part came off and see that the build says so.

**Every reader then had to choose**, and they don't all choose the same way. The build sheet and the garage show what came off. Car search text, the search index and the share card's mod count describe only what is fitted — a build should not keep matching a part it no longer has ([search migration](supabase/migrations/20260919171500_car_search_installed_mods.sql)). The listing provenance line, post mod blocks and the sell-form prefill deliberately do *not* filter, because a removed part is the normal case for all three. In the composer, "Sell this part" now appears on **replaced** as well as removed, and a published update that says a part came off **offers** to mark it off the sheet — an offer, never a consequence: publishing an update is story-telling, the sheet is a record, and letting the first rewrite the second would mean a mistyped block strips a part off a build.

Two things the database now refuses rather than hopes for: `removed_at` is set exactly when `status = 'removed'`, and `save_mod_items` derives it instead of taking it from the client, so re-saving a sheet can't drag the date a part came off forward to today. The delete statement is byte-identical to the previous version — the editor keeps sending removed rows with their status, so omitting a row still means delete. The same migration carries the columns the next two workstreams need (`product_url`, `image_url`, `source_domain`, `ref_price_cents` + `ref_price_currency`, `source_order_item_id`) so the function is re-created once rather than three times.

`DataRow` gained an `end` slot for a row's trailing action, which let both build-sheet row types migrate off hand-rolled `.bline` markup (the recipe ratchet's count drops from 2 to 1). New recipes: `.modrow__ask` and `.modrow--off`. Proof: 684 unit tests, typecheck and lint green; `mod_sheet_atomic_guard` gained a record-identity block and the whole SQL guard suite passes; walked end to end on the dev server — the ask renders in-row with 44px targets, the line moves to "Came off this car", the save keeps the row's id and sets `removed_at`, and the public build sheet drops to six entries and grows its new section. Phone width for the mods editor was not visually confirmed.

## 2026-09-19 — Cooler dark theme (WS7)

The night sheet moves from warm sepia to cool graphite ([PRD §3](docs/DRVN-PRD-2026-09.md)). It was a lit drawing board — `#15130c` paper, `#f0eee5` ink, alpha-ink cut from `240,238,229` — which tinted the shadows of every car photo towards brown; a blue car read faintly warm. It is now `#121418` paper, `#0c0e11` recessed, `#1c1f25` / `#171a1f` plates, `#eceef2` ink, `#8a909b` secondary, `#22262d` media fallback, `#14161a` on-ink, `#262a31` ghost hover, with alpha-ink cut from `236,238,242`. **The day theme, the accent and the status hues are untouched.** Because night is a token remap, the change is one block plus the three places that carry night hexes as literals: the brand page's swatches and night specimen, the Stripe appearance fallbacks in `payment-confirm.tsx`, and the `select` chevron, which is an inline SVG and so can't read a custom property. Two tokens the PRD doesn't list — `--scrim` and `--ink-hover` — follow the palette because they are derived rather than decided (a step under paper-deep, and ink at the day sheet's ~0.91 step); left warm they would have been the two brown edges on a cool sheet. `--photo-filter` is unchanged: it answers how bright a photo sits on a dark page, not what colour the page is. **Contrast re-measured on the switch** and recorded in the CSS and [brand](docs/site/brand.md): ink 15.87:1 on paper and 14.21:1 on tile; `dim` 5.74:1 on paper (up from 5.52) and 5.14:1 on tile (up from 4.95); `on-ink` 15.59:1 on ink and 5.30:1 on the live fill; every status text token still clears 5.7:1 on its own tint. Every pairing held or improved — the cooler sheet is slightly darker, so secondary text gained a little room. Proof: a **new night axe pass** over the five public pages, green — the suite had never once rendered the dark theme, because the theme is a cookie and Playwright's `colorScheme` only sets `prefers-color-scheme`; light-theme visual baselines unmoved at all five viewports; full unit suite, typecheck and lint green; Home, Explore, Marketplace and Garage walked in the dark on the dev server at desktop and phone widths.

## 2026-08-01 — Money correctness: transfers on delivery, reversals everywhere (Rev E items 1–7)

**The clearing window is now real (`0020_transfer_scheduling.sql`).** Transfers no longer fire inside `payment_intent.succeeded` — the webhook records a `transfer_intents` row; buyer-confirmed delivery stamps `available_at = delivered_at + 7 days` (the exact window the ledger has always displayed); pg_cron's `drvn-transfer-worker` marks due intents ready in pure SQL — only while the order is in a deliverable end state, so a dispute freezes the money by construction — and the worker (`src/lib/payments/transfer-worker.ts`, reached via `/api/jobs/transfers` behind `CRON_SECRET`, or the console's Payments → "Run worker now") turns them into Stripe transfers. The Stripe idempotency key stays `transfer:{order_id}`, the same key the legacy path used, so nothing historic can duplicate. Backfill created intents for every captured-but-untransferred order: sellers who sold before onboarding are now `blocked_unpayable` rows the console can see and the worker retries forever (attempts don't increment on the wait state), unblocked eagerly when `account.updated` reports them payable. Stub-era orders were cancelled on record.

**Every refund path reverses the seller's transfer.** Buyer-accepts and seller-cancellation migrated onto `refundOrder`; a lost card dispute books through the new `recordExternalRefund` (the chargeback already took the platform's money — the seller's share is now reclaimed proportionally instead of silently absorbed); dashboard refunds arriving on `charge.refunded` attribute via our refund metadata first, exact-amount fallback second, and anything ambiguous opens a `payment_recoveries` case instead of leaving the order quietly `paid` and double-refundable. Both share one effects core: proportional reversal (cumulative-deterministic keys, so overlapping paths can't double-reverse), fee reconciliation, intent cancellation, recovery on failure.

**Webhook `event.id` dedup** — every event is claimed in `webhook_events` before handling; a fully processed id acknowledges immediately, a crashed first pass reprocesses (handlers are idempotent). **Alerting** — the settlement lines that used to be money-losing log statements now produce recovery cases or blocked intents that stand in an admin queue until a human closes them, alongside the existing Sentry forwarding.

## 2026-08-01 — Admin console: the intervention path (Rev E, Task 1)

DRVN previously had no admin concept at all — no way to force a refund, resolve a stuck dispute, take down a listing, or suspend a seller. This adds the full back-office, gated and audited, in Livesheet's visual language.

**Schema (`0018_admin.sql`, `0019_money_infra.sql`, both applied live and verified).** Admin membership is a separate `admin_users` table with no client-reachable grant or policy — deliberately *not* a flag on `profiles`, whose self-update policy has already been one live money-extraction path (0017). `public.is_admin()` (`stable security definer`, false for null-uid contexts) is used **inside RLS policies** on orders, order items, payments, offers, messages and listings, so the database grants admin visibility declaratively. `admin_audit_log` is append-only for every role including service_role (trigger-enforced). `reports` gives moderation a substrate; listings gained a seller-unwritable `removed` status and profiles gained service-role-only suspension columns, with suspension enforced in the listings SELECT policy (a suspended seller's stock leaves browse; new listings are refused). 0019 adds the money plumbing the refund path and the Rev E money work share: `webhook_events` (event.id dedup), `transfer_intents` (persisted before Stripe is called; doubles as the stuck-funds queue, with `available_at` modelling delivery + clearing hold), `payment_recoveries` (failed reversals and unattributed partials stay open until a human closes them), and explicit refund-adjustment columns on orders (`refunded_cents`, `platform_fee_refunded_cents`) so checkout figures stay frozen and derived numbers subtract. Verified by impersonating a real `authenticated` user — 23 assertions in `supabase/tests/admin_guard.sql`, now also run in CI.

**The one refund path (`src/lib/payments/refunds.ts`).** Built once, correctly, with the admin force-refund as its first caller (the other Rev E paths migrate onto it next): reverses the seller's transfer proportionally via `transfers.createReversal` (separate charges and transfers — `reverse_transfer` doesn't apply), uses per-**order**, cumulative-amount-deterministic idempotency keys (per-intent keys collided across a multi-seller basket's orders — Rev E item 3, fixed at the provider seam), reconciles the platform fee's share of every refund, stamps `order_id` metadata on the refund so the webhook can attribute it, claims the order atomically before any money moves, and records a failed reversal as an open `payment_recoveries` case — negative-balance recovery, not a log line.

**Console (`src/app/(admin)` at `/admin`).** Gated by `getAdminContext()` → real 404 for non-admins (metadata resolved conditionally so even the tab title doesn't confirm the route exists); out of nav and sitemap; every server action re-verifies membership and writes its audit row in the same code path (`auditedAction` — no mutation without an audit entry, reason required). Surfaces: **Overview** (needs-attention KPI deck), **Disputes** (oldest-first queue, over-SLA flagging at 4 days), **order sheet** (money state, dispute block, both parties with history, thread, force refund full/partial + resolve-for-seller), **Orders** (search by id / `pi_…` / username), **Listings** (takedown with seller-visible reason, restore-as-paused), **Users** (suspend/unsuspend; suspension pauses exactly the live stock and unsuspension restores exactly that set), **Reports** (moderation queue), **Payments ops** (recovery cases, transfer pipeline / stuck funds, webhook stream), **Audit** (filterable, append-only).
